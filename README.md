# 🚀 B2B Mini-CRM (Backend)

Серверная часть для CRM-системы управления B2B-продажами. Проект спроектирован с упором на **жёсткий контроль качества обработки лидов (SLA)**, **мгновенную синхронизацию данных в реальном времени** и **отказоустойчивую сессионную аутентификацию**.

---

## 🎯 1. Реализованный функционал и бизнес-логика

* **⚡ Real-time синхронизация (WebSockets):** Реализованы общие сокет-соединения для мгновенного обновления интерфейса у всей команды (например, при перетаскивании карточек на Канбан-доске) и выделенный канал событий по задачам.
* **⏱ Контроль SLA (15 минут):** Автоматическая фиксация просрочки первого ответа менеджера по новому лиду с помощью фоновых задач (`node-cron`) для минимизации оттока клиентов.
* **✅ Управление задачами и активностями (`activity`):** Исключение «забытых» сделок за счёт обязательного планирования звонков, встреч или писем.
* **🏢 B2B-архитектура (`company`, `customer`, `deal`, `funnel`):** Чёткое разделение сущностей на контрагентов и контактных лиц, а также полноценное управление сделками, воронками продаж и их этапами.
* **🔔 Система уведомлений (`notification`):** Реализованы мгновенные уведомления в реальном времени через WebSockets, а также базовая демо-версия отправки писем на электронную почту.
* **👥 Управление пользователями (`user`):** Ролевая модель доступа и управление учётными записями.

---

## 🔐 2. Архитектура аутентификации и сессий

Реализована гибридная JWT-аутентификация с серверным контролем сессий через **Redis**:

* **Хранение токенов:** `Refresh Token` устанавливается бэкендом в защищённые `HttpOnly` куки, а `Access Token` хранится исключительно в оперативной памяти фронтенда (защита от XSS).
* **Управление сессиями в Redis:** При входе создаётся сессия, связывающая `userId`, `refreshToken` и текущий `accessToken`. Сессия отзывается при логауте или автоматически удаляется по TTL.
* **Решение проблемы мультивкладочности (без BroadcastChannel):**
  1. **Плановое обновление (`/refresh` с протухшим access-токеном):** Бэкенд верифицирует refresh-токен и сессию, генерирует новый access-токен, перезаписывает его в Redis и возвращает клиенту в JSON.
  2. **Открытие новой вкладки или F5 (`/refresh` без access-токена в памяти):** Бэкенд проверяет refresh-токен и активную сессию в Redis. Если сохранённый в сессии access-токен ещё валиден, сервер возвращает именно его, не перевыпуская новый.
  * *Результат:* Все открытые вкладки браузера используют один актуальный `Access Token`, а фронтенд остаётся максимально простым без необходимости синхронизировать состояние между вкладками.

## 🗄️ 3. База данных и кэширование

* **PostgreSQL + TypeORM:** Основное реляционное хранилище. Схема спроектирована со строгими связями (`One-to-Many` / `Many-to-One`) и каскадными удалениями для гарантии целостности данных. Реализована ролевая модель (каждый пользователь имеет строго одну роль).
* **Redis:** Используется как высокоскоростное in-memory хранилище для управления сессиями аутентификации и кэширования ответов тяжёлых эндпоинтов.

## 📋 4. В планах (Roadmap)

* **📊 Геймифицированная аналитика:** Модуль отчётов для прозрачной мотивации команды менеджеров, включающий:
  * «Доску почёта» и рейтинг эффективности;
  * расчёт KPI по выручке и конверсии;
  * мониторинг «Зоны риска» по нарушениям SLA.
* **📧 Полноценная система Email-уведомлений:** Доработка почтового модуля (подключение продакшн-провайдера, HTML-шаблоны писем, очереди отправки и расширение триггерных событий).
* **☁️ Интеграция с S3-хранилищем:** Подключение объектного хранилища (AWS S3 / MinIO) для загрузки, хранения и выдачи файлов (договоры, счета, вложения к сделкам и аватары пользователей).

---

## 🛠️ 5. Технологический стек

* **Backend-фреймворк:** Node.js (NestJS) + TypeScript
* **База данных и ORM:** PostgreSQL, TypeORM
* **Кэш и сессии:** Redis
* **Real-time:** Socket.io
* **Планировщик задач:** Node-cron
